# Phase 1: Project Setup & Infrastructure

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Set up the Supabase schema, extensions, and local development environment so all subsequent phases have a clean foundation to build on.

**Architecture:** Custom `ads` schema in the existing Supabase project. SQL migrations managed as versioned `.sql` files. pgTAP for database-level testing.

**Tech Stack:** Supabase (Postgres 15+), pgTAP, Supabase CLI (`supabase`)

### Task 2: Create the `ads` schema migration

**Files:**
- Create: `supabase/migrations/00001_create_ads_schema.sql`

- [ ] **Step 1: Generate a new migration**

```bash
supabase migration new create_ads_schema
```

Expected: Creates a timestamped migration file in `supabase/migrations/`. Rename it to `00001_create_ads_schema.sql` for readability (or keep the timestamp — either works).

- [ ] **Step 2: Write the schema creation SQL**

Write the following into the migration file:

```sql
-- Create the ads schema (separate from public)
CREATE SCHEMA IF NOT EXISTS ads;

-- Grant usage to supabase roles so RPC and PostgREST can access it
GRANT USAGE ON SCHEMA ads TO postgres, anon, authenticated, service_role;

-- Set default privileges so future tables are accessible
ALTER DEFAULT PRIVILEGES IN SCHEMA ads
  GRANT ALL ON TABLES TO postgres, service_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA ads
  GRANT SELECT ON TABLES TO anon, authenticated;
```

- [ ] **Step 3: Apply the migration locally**

```bash
supabase db reset
```

Expected: Local database recreated with the `ads` schema.

- [ ] **Step 4: Verify the schema exists**

```bash
supabase db execute --sql "SELECT schema_name FROM information_schema.schemata WHERE schema_name = 'ads';"
```

Expected: Returns one row: `ads`.

- [ ] **Step 5: Commit**

```bash
git add supabase/migrations/
git commit -m "feat: create ads schema"
```

### Task 3: Enable pgTAP extension for testing

**Files:**

- [ ] **Step 1: Create the migration to enable pgTAP**

### Task 4: Expose the `ads` schema via Supabase API settings

**Files:** None (Supabase Dashboard configuration)

- [ ] **Step 1: Add `ads` to exposed schemas**

In Supabase Dashboard → Settings → API → Exposed schemas, add `ads` to the list. This allows the `supabase-js` client to call RPC functions in the `ads` schema.

Alternatively, if using the CLI config:

```toml
# supabase/config.toml — add under [api]
[api]
extra_search_path = ["public", "ads"]
```

- [ ] **Step 2: Verify RPC access works**

```bash
supabase db execute --sql "
CREATE OR REPLACE FUNCTION ads.ping() RETURNS text AS \$\$
BEGIN RETURN 'pong';
END;
\$\$ LANGUAGE plpgsql SECURITY DEFINER;
"
```

Then test via REST:

```bash
curl -X POST "http://localhost:54321/rest/v1/rpc/ping" \
  -H "apikey: YOUR_LOCAL_ANON_KEY" \
  -H "Content-Type: application/json"
```

Expected: `"pong"`.

- [ ] **Step 3: Drop the test function**

```bash
supabase db execute --sql "DROP FUNCTION ads.ping();"
```

- [ ] **Step 4: Commit config changes**

```bash
git add supabase/config.toml
git commit -m "chore: expose ads schema via Supabase API"
```
